Да. Если считать **Этап 1** именно завершением текущего skeleton, я бы не добавлял пока новые крупные подсистемы. Нужно довести существующие компоненты до замкнутого рабочего контура.

Сейчас я вижу несколько конкретных пробелов.

## 1. `Application` — довести конфигурацию до конца

Это сейчас главный незаконченный участок.

У нас уже есть:

```text
config/
├── config.hpp
├── config_error.hpp
├── json_config_loader.hpp
└── json_config_loader.cpp
```

И `Config` содержит:

```text
instrument
strategy
riskLimits
exchanges
recording
```

Но `Application` должен реально использовать конфигурацию для создания/настройки компонентов.

Нужно:

```text
config.json
    ↓
JsonConfigLoader
    ↓
Config
    ↓
Application
    ├── RiskManager::setLimits()
    ├── ImbalanceStrategy(...)
    ├── StrategyExecutor(...)
    ├── Recording
    └── Exchange configuration
```

То есть сейчас `Application` всё ещё содержит много hardcoded:

```cpp
InstrumentId { 1 }
Quantity { 100'000'000 }
```

и т.д.

**Это первое, что я бы закончил.**

# 9. Strategy configuration

То же самое для:

```cpp
ImbalanceStrategy
```

Сейчас:

```cpp
strategy {}
```

А должно быть:

```cpp
strategy {
    config.strategy.thresholdNumerator,
    config.strategy.thresholdDenominator
}
```

Здесь есть небольшой архитектурный вопрос: `Strategy` сейчас создаётся в initializer list, а `Config` нужно загрузить **до** создания стратегии.

Поэтому нам, скорее всего, придётся немного изменить lifecycle `Application`.

Например:

```text
Application()
    ↓
loadConfig()
    ↓
construct/configure components
```

или использовать `initialize()` после базовой конструкции.

Это я бы отдельно аккуратно проработал, потому что здесь легко получить неудобный порядок инициализации.

Не должно получиться:

```text
Strategy      → config.instrument
MarketData    → 2
```

# 11. Error handling на уровне Application

Сейчас конфиг загрузчик уже возвращает:

```cpp

```

Нужно определить, что делает:

```cpp

```

если конфиг не загрузился.

Я бы **не делал exceptions только ради этого**, если мы уже выбрали `expected`.

Но тут есть важный API-вопрос:

```cpp
Application();
```

не может сообщить об ошибке загрузки.

Поэтому для законченного skeleton я бы рассмотрел:

```cpp
static std::expected<Application, Error> create(
    const std::filesystem::path& configPath);
```

либо:

```cpp
explicit Application(Config config);
```

а загрузку сделать снаружи:

```text
main
 │
 ├── JsonConfigLoader::load()
 │
 └── Application(config)
```

Мне второй вариант нравится больше.

## И я бы следующим шагом занялся именно `Application`

Потому что сейчас у нас уже есть практически все необходимые компоненты:

```text
Config
RiskManager
Strategy
StrategyExecutor
OrderManager
Position
MarketData
Execution
Recording
```

Но **`Application` ещё не связывает их через Config в единый runtime**.

Я бы сейчас сделал его точкой, где окончательно формируется:

```text
                         Config
                           │
                           ▼
                     ┌───────────┐
                     │Application│
                     └─────┬─────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   Market Data          Strategy           Execution
        │                  │                  │
        ▼                  ▼                  ▼
   OrderBook           Executor         OrderManager
        │                  │                  │
        └─────────────► MarketEvent ◄─────────┘
                                           │
                                           ▼
                                       Position
```

После этого **Этап 1 можно будет считать действительно законченным skeleton**, а уже следующим этапом спокойно заниматься robustness и `Position/PnL/Portfolio`.
